#Exercise 1
For Exercise 1, we implemented validateLTS, that checks if each individual constraint about the LTS is valid.
In order to being able to test the single properties in the followinng exercise, the function is an And conjunction of all the properties.

Here are the factors that would result in an invalid IOLTS according to the definition:
1. Empty State Set: States set Q is empty (Q = []).
2. Initial State Membership: Initial state q0 does not belong to Q (q0 notElem Q).
3. Duplicate States: States list Q contains duplicate state identifiers.
4. Non-Disjoint Labels: Input labels (LI) and Output labels (LU) overlap (LI intersect LU /= []).
5. Reserved Labels in Sets: LI or LU contain reserved special labels ("tau" or "delta").
6. Invalid Label Prefixes: Inputs do not start with '?' or outputs do not start with '!'.
7. Duplicate Labels: Input or output label lists contain duplicate entries.
8. Invalid Transition States: A transition (s1, l, s2) uses a state s1 or s2 not in Q.
9. Invalid Transition Labels: A transition label l is not in LI, LU, or equal to "tau".
10. Duplicate Transitions: Transition relation T contains duplicate transitions.

#Exercise 2
For Exercise 2, we built random generators to produce valid and invalid transition systems for QuickCheck testing.
The valid generator, genValidIOLTS, creates a non-empty set of states starting from 1, picks input and output labels from separate pools to avoid overlap, and generates unique transitions using only existing states and valid labels.
To perform negative testing, we also created genInvalidIOLTS, which takes a valid system and deliberately introduces a single fault, such as using an invalid initial state, overlapping label sets, or referencing missing states. 
We then used QuickCheck to confirm that all generated valid systems pass validateLTS, while all invalid systems are correctly rejected.

Design Decisions:
For Exercise 3, we implemented the straces function to compute suspension traces for an IOLTS, taking quiescent states into account by dynamically adding delta self-loops.
To prevent infinite recursion caused by graph cycles or tau loops, we bounded the trace search depth and decremented the depth limit on every transition step.
We then built genStrace to randomly sample generated suspension traces for QuickCheck testing.
Finally, we verified the implementation across three structural properties: confirming that the empty trace is always present, checking prefix closure for all suspension traces, and ensuring that traces contain only valid input, output, or delta labels.

#Exercise 4

For Exercise 4, we implemented the `after` function to find all possible states reachable after a given trace.
We used `tauClosure` to include states reachable through internal tau transitions, and `foldl` to process the actions in order. Delta is handled separately by keeping only quiescent states, where no output or tau transition is possible.
We tested the implementation with concrete cases covering tau, delta, nondeterminism, and invalid traces. We also tested it using ordinary traces from `LTS.hs` and suspension traces from Exercise 3.
Finally, we used QuickCheck with randomly generated IOLTS models. All 12 concrete tests passed, and both QuickCheck properties passed 100 tests each.

Time Spent: 90 min

#Exercise 5

For Exercise 5, we created an IOLTS model representing the correct behavior of the door, including the open, closed, and locked states.

We implemented `testLTSAgainstSUT` to compare the outputs of the door implementations with the outputs allowed by the specification. We reused the `after` function from Exercise 4 and explored possible command sequences, keeping track of the implementation's internal state.

To avoid infinite loops, we kept track of previously visited state combinations. This also allowed us to test longer sequences where some bugs only appear after several commands.

We tested all eight door implementations. The correct implementation (`doorImpl1`) was accepted, while the other seven were rejected due to incorrect outputs or runtime errors.

   Bugs found:
- `doorImpl2`: Returns `opened` instead of `closed` after `close`.
- `doorImpl3`: Remains in the wrong state after `unlock`, causing a later command to fail.
- `doorImpl4`: Uses incorrect behavior for the `lock` and `unlock` commands.
- `doorImpl5`: Returns `open` instead of `opened`.
- `doorImpl6`: The door becomes stuck after repeated opening and closing.
- `doorImpl7`: An `unlock` command eventually produces an incorrect keycode error.
- `doorImpl8`: An `open` command fails after a longer sequence of valid commands.

Time Spent: 100 min

#Exercise 6

For Exercise 6, we implemented `visualizeLTS` to display an IOLTS as an ASCII representation in the terminal. We chose this approach because it is simple and does not require additional libraries or external software.

The function displays each state with its outgoing transitions and marks the initial state with an arrow. Input and output labels are shown with their corresponding prefixes, while internal tau transitions are displayed separately.

We also implemented `visualizeRandomLTS`, which uses QuickCheck's `generate` function to visualize randomly generated IOLTS models from Exercise 2.

We tested the visualization with a predefined model, a model containing a terminal state, and a randomly generated IOLTS. All three produced the expected output.
